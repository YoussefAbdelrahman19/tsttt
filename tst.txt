3. PROJECT AREA 1 – VULNERABILITY MANAGEMENT AUTOMATION
======================================================================

Description:

The first part of the project is a vulnerability management automation workflow.

The main goal is to reduce manual ticket handling and avoid creating unnecessary individual tickets for every vulnerability finding.

Instead of opening many separate tickets, vulnerability findings should be grouped based on the device group.

The automation should then identify the responsible team and automatically create or update the related Jira ticket.

The solution should explain the full Logic App workflow from receiving the vulnerability findings until the final Jira ticket is created or updated.

The presentation must explain WHY this approach is useful.

Key reasons include:

- Reducing manual work
- Reducing ticket noise
- Avoiding unnecessary duplicate tickets
- Grouping related vulnerability findings together
- Improving ownership
- Making remediation easier for infrastructure teams
- Making tickets more readable and actionable
- Improving consistency in the vulnerability management process
- Reducing the chance of findings being missed
- Improving operational efficiency

The Logic App workflow should include the following stages:

1. Receive vulnerability findings
2. Validate required information
3. Identify the affected device
4. Identify the related device group
5. Group related findings based on the device group
6. Identify the responsible team
7. Check if a related Jira ticket already exists
8. If a ticket exists, update it where appropriate
9. If no ticket exists, create a new Jira ticket
10. Assign the ticket to the correct responsible team
11. Add the relevant vulnerability information
12. Log the result
13. Handle missing or incorrect information
14. Handle Jira or Logic App failures
15. Support testing and validation before production

Create a visual flow similar to:

Vulnerability Findings
        |
        v
Validate Input
        |
        v
Identify Device
        |
        v
Identify Device Group
        |
        v
Group Related Findings
        |
        v
Map Device Group to Responsible Team
        |
        v
Check Existing Jira Ticket
        |
        v
Existing Ticket?
   /            \
 Yes             No
  |               |
  v               v
Update Ticket    Create New Ticket
  |               |
  \               /
        v
Assign Responsible Team
        |
        v
Add Vulnerability Details
        |
        v
Log Result
        |
        v
Monitoring / Error Handling

The presentation should explain the design decisions behind:

- Grouping strategy
- Device group logic
- Responsible team mapping
- Duplicate ticket prevention
- Ticket lifecycle
- Error handling
- Retry logic
- Logging
- Failure monitoring
- Validation
- Manual review where needed

Also explain edge cases such as:

- Device group is missing
- Responsible team mapping does not exist
- Jira ticket creation fails
- Existing ticket lookup fails
- Required vulnerability information is missing
- Duplicate ticket is detected
- Logic App action times out
- Unexpected data format is received

Do not invent Jira fields, Logic App connector fields, APIs, schema names, or implementation details that are not provided.

If exact technical values are unknown, clearly label them as:

"Implementation-dependent and must be validated in the target environment."

======================================================================

Description:

The second part of the project is focused on security detection engineering.

The goal is to design better security use cases and KQL detections for Microsoft Sentinel and Defender XDR.

The presentation should explain that detection engineering should start from attacker behaviour and security objectives, not only from writing a KQL query.

Create a clear detection engineering lifecycle:

        v

        |
        v

        |

For every detection use case, the presentation should explain:

- Use case name
- Security objective
- Attacker behaviour
- Why the use case is important
- Required data sources
- Required events
- Important entities
- Correlation logic
- Time window
- KQL approach
- MITRE ATT&CK mapping
- False positives
- Testing method
- Tuning requirements
- Recommended severity
- Limitations
- Production readiness checks

Explain strong detection design principles such as:

- Multi-stage correlation
- Identity + endpoint correlation
- Authentication + privilege change correlation
- Suspicious activity followed by persistence
- Cloud control-plane activity followed by security-impacting changes
- Strong entity correlation
- Time-bounded event chaining
- Behaviour-based detections instead of simple threshold-only detections

Prefer strong identifiers where they are available, including:

- AccountObjectId
- UPN
- DeviceId
- SessionId
- CorrelationId
- IP address
- SHA256
- AppId
- ServicePrincipalId
- ResourceId

Explain why stable identifiers are better than weak correlation fields.

The presentation should also explain join logic:

- Use inner joins when both stages are required for the detection
- Use leftouter only when the second dataset is enrichment
- Avoid broad joins that create weak correlation
- Keep time windows realistic
- Avoid correlating events only because they happened close together

For KQL:

- Do not invent tables
- Do not invent columns
- Do not invent KQL functions
- Do not invent schema
- Do not assume data availability
- Clearly mark anything that requires validation
- Explain every join
- Explain important filters
- Explain time windows
- Explain tuning logic
- Explain false-positive handling

If KQL examples are included, clearly label them as:

"Example logic only – table and field availability must be validated in the target environment."
