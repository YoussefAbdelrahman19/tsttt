IBM Generative & Agentic AI Badge Application

1. Generative AI Client or Project

I used generative AI as a support tool during a security automation project.

The project was focused on improving the vulnerability management process by using a Logic App to automate the ticket creation and assignment process.

One of the main problems was that the vulnerability findings should not create a separate ticket for every single finding. The findings needed to be grouped in a better way based on the device group. After the grouping, the automation should create the Jira ticket and assign it to the correct responsible team.

I used AI mainly to help me design the flow of the Logic App and think about how the different steps should work together.

For example, I used it to help me think about:
- how the findings should be grouped based on the device group
- how the Logic App should check which team is responsible for each group
- how the conditions and loops should be designed
- how the flow should create the Jira ticket automatically
- how the ticket should be assigned to the correct team
- how to avoid unnecessary duplicate tickets
- how the flow should behave if some information is missing or if one step fails

I also used AI when I was comparing different ways to build the same logic. This helped me think about the flow before I started implementing everything and also helped me during troubleshooting when I needed to understand why one part of the automation was not working as expected.

I did not use AI to make the final decisions by itself. I used it mainly as a technical assistant to help me design the process faster, review different implementation ideas, and improve the overall flow.

The final goal of the project was to reduce manual work, make the vulnerability ticketing process more structured, group related findings together, and make sure each Jira ticket is created and assigned to the correct team automatically.

4. Approach, Methods, and Tools

My approach is normally very practical.

I first try to understand the problem clearly before using AI.

For the Logic App automation project, I first understood how the vulnerability management process should work from start to finish.

I defined how the findings should be grouped, how the correct team should be identified, when a Jira ticket should be created, and how the ticket should be assigned.

After that, I used AI to help me design the Logic App flow and compare different ways to implement the logic.

For detection engineering, I normally start from the use case.

I define:
- what activity I want to detect
- what the attack behaviour should look like
- what data sources are available
- what information I can use for correlation
- what could create false positives

Then I use AI to help me think about the KQL logic or improve an existing query.

I never use the first generated query directly.

I review the query, check the syntax, check the tables and fields, run it in Sentinel or Defender XDR, and then review the results.

If the query is too noisy or does not detect the expected behaviour, I change the logic and test it again.

For MITRE ATT&CK gap analysis, I reviewed the existing detection coverage and compared it with the relevant techniques and sub-techniques.

AI helped me organise the work and think about possible detections for the missing areas.

For new use cases, I also used AI to think about the full detection flow from the attack behaviour until the final KQL and testing steps.

The main tools I used were Microsoft Sentinel, Defender XDR, Defender for Endpoint, Entra ID, KQL, Logic Apps, Jira, Azure security services, and MITRE ATT&CK.

My normal process is:

understand the problem, design the idea, use AI to support the work, review the output, test it, improve it, and validate the final result.


5. Management of Risks and AI Ethical Concerns

When I use generative AI for security work, I always treat the output as a suggestion and not as a final answer.

One of the main risks is that AI can give technically incorrect information.

For example, it can suggest a KQL field that does not exist, use the wrong table, create a weak correlation, or suggest a logic that does not match the real environment.

Because of this, I always validate the technical result myself.

For KQL, I test the query directly in Sentinel or Defender XDR.

I check the tables, fields, joins, filters, time windows, and the results.

I also make sure the query is not creating unnecessary false positives and that it is really detecting the behaviour that I want.

For MITRE ATT&CK mapping, I check that the technique or sub-technique really matches the behaviour of the detection.

For new use cases, I review both the attacker side and defender side to make sure the logic is realistic and useful.

For automation, like the Logic App vulnerability management project, I test the conditions, grouping logic, Jira ticket creation, and assignment before depending on the automation.

This is important because a wrong condition can create the wrong ticket or send it to the wrong team.

I also keep human control for important security decisions.

AI should support the engineer, but it should not make high-impact decisions by itself.

For example, I would not depend on AI alone to decide that an account is compromised, isolate a device, close an incident, or perform containment.

My approach is simple: use AI to support the work, validate the technical output, test everything important, keep human control, and make sure the final result is correct before using it.
