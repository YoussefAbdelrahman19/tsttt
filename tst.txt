SLIDE 2 — PROJECT OBJECTIVE
--------------------------------------------------

Title:
Project Objective

Content:
The goal of this project is to reduce manual work in vulnerability management by automating the ticketing process.

Main objectives:
- Group related vulnerability findings based on the device group
- Avoid creating unnecessary individual tickets
- Identify the responsible team automatically
- Create Jira tickets automatically
- Assign tickets to the correct team
- Improve ticket quality and ownership
- Reduce manual effort
- Improve consistency and traceability

Why it is needed:
Without automation, security teams can spend significant time creating, reviewing, grouping, and assigning tickets manually.

SLIDE 5 — END-TO-END LOGIC APP FLOW

SLIDE 6 — GROUPING LOGIC
--------------------------------------------------

Title:
Grouping Vulnerability Findings

Content:
The main design decision is to group vulnerability findings based on the device group.

Why device-group-based grouping:
- Devices in the same group normally have the same operational owner
- Related findings can be handled together
- Ticket volume is reduced
- Remediation becomes easier to manage
- Ownership is clearer
- Teams get a better view of related vulnerabilities

Example logic:

Finding A → Device Group: VM Servers
Finding B → Device Group: VM Servers
Finding C → Device Group: AVD

Result:

VM Servers → One grouped workflow / ticket
AVD → Separate grouped workflow / ticket

Important:
The exact grouping logic should be validated against the operational process before production.

Design:
Use a before/after comparison.

Before:
10 findings → 10 tickets

After:
10 findings → 2 or 3 grouped tickets based on device group

SLIDE 8 — DUPLICATE TICKET PREVENTION
--------------------------------------------------

Title:
Duplicate Ticket Prevention

Content:
Before creating a new Jira ticket, the workflow should check whether a related ticket already exists.

Purpose:
- Avoid repeated tickets for the same problem
- Reduce noise
- Avoid duplicate remediation work
- Keep the ticket history in one place

Decision logic:

Grouped Finding
        ↓
Search Existing Jira Ticket
        ↓
Ticket Found?
   /            \
 Yes             No
  ↓               ↓
Update Existing  Create New
Ticket           Ticket

Important:
The duplicate logic must use stable matching criteria.

Possible matching criteria may include:
- Device group
- Vulnerability identifier
- Active ticket status
- Time window
- Defined correlation key

The exact criteria are implementation-dependent and must be validated.

Design:
Use a decision-tree diagram.

SLIDE 11 — RETRY AND RESILIENCE
--------------------------------------------------

Title:
Retry Logic and Resilience

Content:
Temporary failures should not immediately cause the full workflow to fail.

Use controlled retry where appropriate.

Examples:
- Temporary Jira API failure
- Network timeout
- Connector throttling
- Short service outage

Design principles:
- Use limited retry
- Use exponential or platform-supported retry where appropriate
- Do not retry permanent validation errors
- Record retry attempts
- Alert when the maximum retry count is reached

Design:
Use a small flow:
Failure → Retry Eligible? → Retry → Success / Escalate

SLIDE 3 — WHY DETECTION ENGINEERING NEEDS STRUCTURE
--------------------------------------------------

Title:
Why a Structured Detection Engineering Process Is Needed

Content:
A detection rule is not only a KQL query.

A strong detection requires:
- Clear security objective
- Real attacker behaviour
- Correct telemetry
- Correct entities
- Strong correlation
- Correct time window
- Testing
- False-positive analysis
- Tuning
- Validation
- Monitoring

Weak detections often fail because:
- They rely on a single weak signal
- They use broad thresholds
- They correlate unrelated events
- They use unstable identifiers
- They are not tested
- They are mapped to MITRE incorrectly

SLIDE 5 — START WITH ATTACKER BEHAVIOUR
--------------------------------------------------

Title:
Start with Behaviour, Not with KQL

Content:
Before writing KQL, define what the attacker is doing.

Questions:
- What is the attacker trying to achieve?
- Which stages should be visible?
- Which events should exist?
- Which entities connect the events?
- What is normal behaviour?
- What makes the activity suspicious?
- Which activity is required for strong confidence?

Example:
Suspicious authentication
→ privilege-related action
→ persistence-related change

The detection should model the behaviour first.

Design:
Use an attack chain graphic with 3–4 stages.

SLIDE 7 — ENTITY CORRELATION
--------------------------------------------------

Title:
Strong Entity Correlation

Content:
Correlations should use stable identifiers when available.

Preferred examples:
- AccountObjectId
- UPN
- DeviceId
- SessionId
- CorrelationId
- IP address
- SHA256
- AppId
- ServicePrincipalId
- ResourceId

Why:
Stable identifiers reduce incorrect matches.

Avoid:
- DisplayName-only correlation
- Broad IP-only correlation
- Username fragments
- Time-only correlation

Design:
Use an entity graph:
User ↔ Session ↔ Device ↔ IP ↔ Application

--------------------------------------------------
SLIDE 8 — KQL DESIGN PRINCIPLES
--------------------------------------------------

Title:
KQL Design Principles

Content:
KQL should implement the detection logic clearly and efficiently.

Principles:
- Use only validated tables and fields
- Keep filters early where possible
- Use meaningful time windows
- Correlate required stages
- Avoid weak joins
- Avoid unnecessary complexity
- Keep the query readable
- Document assumptions

Join guidance:
- inner join when both stages are required
- leftouter only for enrichment
- avoid broad joins

Important:
Example queries must be validated against the real schema.

Design:
Use a split diagram:
Required Correlation vs Enrichment

SLIDE 9 — MULTI-STAGE DETECTION
--------------------------------------------------

Title:
Multi-Stage Detection Logic

Content:
High-value detections often become stronger when multiple related stages are correlated.

Example pattern:

Stage 1:
Suspicious authentication

Stage 2:
Privilege or administrative action

Stage 3:
Persistence or security-impacting change

Correlation:
Same user / session / device / resource
within a realistic time window

Value:
This is stronger than alerting on only one generic event.

Design:
Use a three-stage attack chain.

SLIDE 12 — FALSE POSITIVE ANALYSIS
--------------------------------------------------

Title:
False Positive Analysis and Tuning

Content:
A detection is not production-ready until expected legitimate behaviour is understood.

Questions:
- Which admin activity can match?
- Which automation can match?
- Which service accounts can match?
- Which maintenance activity can match?
- Does normal business activity create noise?

Tuning approaches:
- Stronger correlation
- Better entity matching
- Better time windows
- Required event chaining
- Additional contextual conditions

Do not simply exclude large populations without understanding the behaviour.

SHORT DESCRIPTION TO USE WHEN SHARING THE DELIVERABLE
======================================================================

This deliverable covers two practical security engineering workstreams.

The first presentation explains a vulnerability management automation design using Azure Logic Apps and Jira. It focuses on grouping vulnerability findings by device group, automatic team mapping, Jira ticket creation and assignment, duplicate prevention, error handling, monitoring, testing, and operational value.

The second presentation explains a structured detection engineering and MITRE ATT&CK gap-analysis approach for Microsoft Sentinel and Defender XDR. It covers attacker-behaviour-based use cases, telemetry validation, KQL design, event correlation, testing, false-positive tuning, MITRE mapping, coverage gaps, new detection opportunities, and continuous improvement.

Generative AI is presented as a support tool for design, analysis, troubleshooting, documentation, and engineering ideas. The final technical implementation, testing, and security decisions remain under human control.
